# AI Action Guardrail & Governance Platform

**PS-3.1 — The Action Guardrail.** A guardrail layer that evaluates every agent
tool-call/action against a policy ruleset *before* it executes, with three
possible outcomes: `BLOCK`, `REQUIRE_HITL`, `LOG_AND_ALLOW`. Every decision is
recorded in a persistent audit log.

## Architecture

```
User / Demo UI (Streamlit)
        ↓
   FastAPI API (backend/main.py)
        ↓
Guardrail Evaluator (backend/guardrails/evaluator.py)
        ↓
Policy Engine (backend/guardrails/policy_engine.py)  ← policies/policies.yaml
        ↓
Decision: BLOCK / REQUIRE_HITL / LOG_AND_ALLOW
        ↓
Tool Executor → Mock Tools (backend/tools/simulator.py)  [only on allow/approve]
        ↓
SQLite Audit Log (backend/database/db.py)
```

## Why this stack

- **FastAPI**: async, automatic OpenAPI docs at `/docs`, matches the requester's background.
- **Streamlit**: fastest way to a polished, interactive dashboard for this scope.
- **Raw `sqlite3`** (no ORM): the audit table is simple and one-purpose; an ORM
  would add abstraction without adding clarity — easier to explain line-by-line
  in an interview.
- **PyYAML + Pydantic**: policies are data, not code — new rules are added by
  editing YAML, never by touching Python.
- **No LLM dependency**: the guardrail is a deterministic policy engine. An LLM
  adds no value to "is record_count > 100" and would only add cost, latency,
  and a false sense of scale. `OPENAI_API_KEY` is wired into config as optional
  for future extension (e.g., LLM-explained rejection reasons) but is never
  required for the core system to run.

## Policy priority strategy

When multiple rules match one action, outcomes are resolved by
**fail-closed severity**: `BLOCK` > `REQUIRE_HITL` > `LOG_AND_ALLOW`. This
means the safest outcome always wins — you can never accidentally allow
something a stricter rule would have blocked. If several rules share the same
outcome, the first one listed in `policies.yaml` wins (explicit author
control via file order). If **no** rule matches, the safe default is
`LOG_AND_ALLOW` (never a silent block, never a silent full-access) — matching
the spec's default policy.

## 2-minute explanation for the interviewer

"I built a guardrail layer that sits between an AI agent and the tools it's
allowed to call — a database, email, or file system. Every action the agent
wants to take is first submitted as a structured request to a FastAPI
endpoint. That request goes through a policy engine that loads rules from a
YAML file — for example, 'block database deletes over 100 records' or
'require human approval for emails to external domains'. Each rule has a
condition and an outcome: block, require human approval, or log-and-allow.

If multiple rules match the same action, I resolve it with a fail-closed
priority — block always wins over HITL, which always wins over allow — so the
system can never accidentally under-restrict. If nothing matches, the default
is safe: log and allow, never a silent full block or a silent bypass.

Every single decision — matched or not — is written to a SQLite audit table
with the full context: timestamp, agent, parameters, matched policy, and
outcome. Sensitive parameters like passwords are redacted before they're ever
persisted or shown.

For actions requiring human approval, I built a simple pending-queue: the
action is stored as `pending_approval`, shown in the Streamlit dashboard with
its risk reason, and a reviewer can approve or reject it. Approval triggers
the actual (simulated) tool execution; rejection permanently blocks it.

Nothing here actually deletes real data or sends real email — I built mock
tools that simulate execution so the whole system is safely demonstrable.
The demo runner hits the real API with the 5 required scenarios and shows
pass/fail against expected outcomes, so there's no hardcoded demo path — it's
the same code that would run in production."

## Likely interviewer questions

1. **Why not enforce this guardrail inside the LLM prompt instead of a separate layer?**
   Prompt-level controls are advisory and can be bypassed by adversarial
   inputs or model drift. This layer sits *outside* the model, between the
   agent's decision and real-world side effects, so it's enforced
   deterministically regardless of what the LLM was told or how it was
   jailbroken.

2. **How do you handle a rule that needs a field the action doesn't have?**
   `_field_value` returns `None` for a missing field, and the operator layer
   treats `None` as "no match" rather than raising — a malformed/incomplete
   action fails to match specific rules and falls through to the safe
   default (log_and_allow), never crashes the evaluator.

3. **What happens if two rules on the same action_type both say BLOCK but for different reasons?**
   `resolve()` sorts by outcome priority, then by YAML list order for ties —
   so the first BLOCK rule declared in the file is the one recorded as
   `matched_policy`. This is deterministic and testable.

4. **Why SQLite and not Postgres?**
   Scope and reviewability — this needs to run locally with zero setup. The
   `db.py` module is the only place that talks to storage, so swapping in
   Postgres later is a contained change, not a rewrite.

5. **How would you extend this to a new action type, e.g. `api_call`?**
   Add a case to `ActionType` enum, add a YAML rule with
   `action_type: api_call`, and a `MockApiTool` + dispatch case in
   `ToolExecutor`. The policy engine itself needs zero changes — that's the
   point of keeping conditions generic and data-driven.

6. **How do you keep this production-safe if a policy YAML has a typo?**
   `PolicyEngine._apply_operator` raises on unknown operators; that's caught
   per-rule in `evaluate()` and logged as a warning, skipping only the broken
   rule rather than crashing action evaluation for everyone — the guardrail
   fails safe, not open, and not down.

7. **Why is `human_decision` stored as a string like `approved_by:jane` instead of a separate reviewer_id column?**
   Given the "no complicated auth system" scope, this was the simplest way to
   capture who/what without adding a users table. In a real system I'd have
   an authenticated reviewer identity and a separate `reviewed_by` column.

8. **What's not executed if an action is BLOCKed?**
   The tool executor is never called — `evaluate_and_process` branches before
   `_execute()` is reached, so there's no code path where a blocked action's
   side effects can occur, even accidentally.

9. **How do you prevent sensitive data from leaking into the dashboard?**
   `sanitize_parameters()` in `db.py` redacts a configurable set of sensitive
   keys (password, ssn, api_key, etc.) *before* the data is ever written to
   SQLite — so it's not just hidden in the UI, it never touches disk
   unredacted.

10. **How would you scale this to thousands of actions/sec?**
    Move from SQLite to Postgres with connection pooling, make policy
    evaluation stateless/horizontally scalable behind the FastAPI layer
    (already true — `PolicyEngine` holds no per-request state), and move the
    audit write to an async queue (e.g., Kafka) so evaluation latency isn't
    coupled to write latency — while still writing synchronously enough to
    guarantee an audit record exists before execution, which is a hard
    requirement here.
